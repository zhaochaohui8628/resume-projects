## 1. 目标（用户给定的 7 阶段路线）

| 阶段 | 内容 | 目标 |
|---|---|---|
| P1 | 冷启动：LLM 生成 query–正样本对 + 简单负例，双塔 InfoNCE 微调 | 拿到能做向量检索的初版双塔，用于挖候选 |
| P2 | `BM25 + 微调双塔` 多路召回取并集 topN → LLM 语义判别清洗真难负例（甄别规范效力/限定条件/剔除假阴性） | 产出干净的「正样本 + 真难负例」集，**专供精排，不入双塔** |
| P3 | 用清洗后的正+真难负训练 CrossEncoder（BCE） | 教师模型，啃 hard case；要有评估看提升 |
| P4 | 冻结教师，同数据做 **pairwise 软 margin 蒸馏** 回双塔 | 把教师的相对排序能力迁移到双塔，提升 MRR |
| P5 | 用蒸馏后新版双塔再挖一轮难负例 → 清洗 → 扩充教师训练集 → 二次蒸馏 | 迭代提升 |
| P6 | 融合优化：优先 RRF；不如 BM25 单跑则改凸组合（温莎截断 min-max 全局归一）+ α 网格寻优 | 定最终融合配置 |
| P7 | 黄金评测集（1000+，长尾/模糊/边界对抗），微调评估 + ragas | 简历数字 |

### 3.3 检索对照（val **43 条**：直问 30 + 口语 13；全部 cand=10 / top_k=5）

| 配置 | hit@5 | MRR | nDCG@5 |
|---|---|---|---|
| BM25-only | 0.884 | 0.807 | 0.827 |
| 基座塔 · 纯向量 | 0.884 | 0.759 | 0.786 |
| 基座塔 · RRF | 0.954 | 0.798 | 0.834 |
| 基座塔 · 凸组合 α=0.9 | 0.954 | 0.846 | 0.871 |
| **双塔 · 纯向量** | **1.000** | **0.867** | 0.900 |
| 双塔 · RRF | 0.977 | 0.846 | 0.877 |
| 双塔 · 凸组合 α=0.9 | 1.000 | 0.888 | 0.916 |
| **双塔 · 凸组合 α=0.4（最优）** | **1.000** | **0.895** | **0.922** |
| 双塔 · 凸组合 α=1.0（= 纯 BM25 排序） | 0.884 | 0.810 | 0.827 |

**三条结论**：
1. **双塔微调在纯语义通道上收益显著**：MRR 0.759 → **0.867（+14.2% 相对）**、hit@5 0.884 → 1.000。
   （旧项目的同类实验只有 +4.4%，主因是旧数据用模板句、语义增益被 BM25 稀释。）
2. **RRF 优于 BM25 单跑，但明显不如凸组合**：RRF 0.846 vs 凸组合 0.895（−5.5% 相对 MRR）。
   按用户规则"RRF 不敌 BM25 才换凸组合"的判定条件**并未触发**（0.846 > 0.807），
   但凸组合大幅领先 —— **建议直接采用凸组合**，此点需用户确认（见第 6 节风险 6）。
3. **α 最优 = 0.4**（MRR 0.895），说明微调后的向量通道已能与词面通道分庭抗礼；
   α∈[0.3, 0.9] 区间 MRR 波动仅 0.888~0.895，**不敏感**，工程上取值稳健。

> ⚠️ **上表（3.3）是旧语料 val 43 条的结果，已降级为历史参考，不再作为定稿依据。**
> 融合方式的定稿依据是下一节（3.3b）——黄金集是真实口语问句分布，而 val 的问句"照着条款写"，
> 会系统性低估词面通道（实测已导致 α 结论从 0.4 反转到 0.9）。

### 3.3b 黄金集融合对照（**500 条自然语言问句**，cand=20 / top_k=10，2026-09-11 第七轮）

脚本 `scripts/eval_fusion_gold.py`（17 个配置全扫，约 4 分钟），结果 `data/phase7/fusion_gold.json`。

| 配置 | hit@5 | MRR | nDCG@5 |
|---|---|---|---|
| BM25-only（α=1.0） | 0.934 | 0.8538 | 0.8718 |
| 纯向量（α=0.0） | 0.836 | 0.6982 | 0.7272 |
| RRF k=10 | 0.922 | 0.8220 | 0.8439 |
| RRF k=20 | 0.922 | 0.8185 | 0.8417 |
| RRF k=60 | 0.918 | 0.8174 | 0.8393 |
| RRF k=100 | 0.918 | 0.8174 | 0.8393 |
| **凸组合 α=0.9（最优）** | **0.936** | **0.8612** | **0.8773** |

**三条结论**：

1. **凸组合胜出**：最优凸组合 α=0.9（MRR 0.8612）vs 最优 RRF k=10（0.8220），
   **+4.8% 相对**。与旧语料 +5.5% 方向一致，结论稳健。
2. **⭐ RRF 在黄金集上不如 BM25 单跑**（0.8220 < 0.8538）——这**正式触发了用户原定的
   "RRF 不敌 BM25 才换凸组合"条件**。旧语料上该条件未成立（0.846 > 0.807），当时只能
   写成"建议采用、待用户确认"；现在条件成立，**采用凸组合名正言顺**（风险 6 可关闭）。
3. **RRF 对 k 不敏感**：k=10→100 的 MRR 仅 0.8220→0.8174，调 k 救不回与凸组合的差距。

**场景分层**（各自最优配置，MRR）：

| 场景 | n | RRF k=10 | 凸组合 α=0.9 | 差值 |
|---|---|---|---|---|
| 长尾 | 200 | 0.7781 | **0.8394** | **+6.1pt** |
| 模糊 | 150 | 0.8388 | **0.8458** | +0.7pt |
| 对抗 | 150 | 0.8638 | **0.9057** | +4.2pt |

凸组合在**三类场景全面领先**，长尾收益最大（冷门条款更依赖融合打分而非名次相加）。

### 3.3c 黄金集重训双塔后的融合对照（2026-09-11 第七轮，**当前最优**）

用黄金集 1000 条（+ hard negatives）继续训练 dual_p1 后，融合格局发生**根本变化**：

| 配置（MRR） | dual_p1（重训前） | dual_gold（v1 纯黄金 1000） | dual_mix（v2 混合 1422） |
|---|---|---|---|
| 纯向量（α=0.0） | 0.6982 | 0.8689 | **0.8698** |
| BM25-only（α=1.0） | 0.8538 | 0.8538 | 0.8538 |
| RRF k=10 | 0.8220 | **0.9106** | 0.9025 |
| 凸组合最优 | 0.8612（α=0.9） | 0.9135（α=0.3） | **0.9142（α=0.3）** |
| 凸组合 hit@5 | 0.936 | 0.952 | **0.954** |

**四条结论**：

1. **纯向量 0.698 → 0.869（+24.5% 相对），首次反超 BM25-only（0.854）**——向量塔从"拖累"变成
   可与词面通道并列的主通道，这是本次重训的核心收益（此前它是融合里最弱的一环）。
2. **融合最优 MRR 0.861 → 0.914（+5.3pt）**，hit@5 0.936 → 0.954。
3. **α 最优从 0.9 移到 0.3**：向量塔变强后应给它更高权重（α 是 BM25 侧权重，α 越小向量权重越高）。
   ⚠️ 3.3b 表的 α=0.9 是"重训前"的结论，重训后作废。
4. ⭐ **RRF 基本追平凸组合**：v1 上 RRF 0.9106 vs 凸组合 0.9135（仅差 0.3%），
   且 RRF 的 hit@5 更高（0.964 vs 0.952）。**RRF 0.9106 已远超 BM25-only 0.8538，
   用户原定"RRF 不敌 BM25 才换凸组合"的切换条件不再成立** —— 按该规则现在应回到 **RRF（k=10）**。
   此项需用户裁定（凸组合仍以 +0.3% MRR 微弱领先，但 RRF 免调参、对 k 不敏感）。

**v1 vs v2**：差异在噪声内（凸组合 0.9135 vs 0.9142），但 v1 的 RRF 明显更好（0.9106 vs 0.9025）。
**推荐采用 dual_gold（v1）**——更贴合"用黄金集训练"的目标，且 RRF 表现更好。

**训练配置**：继续训练（从 dual_p1 出发）· InfoNCE（temperature 0.05）·
数据 = 黄金集 1000 条 + 每条 4 个 hard negatives（用 dual_p1 检索 top12 挖掘，剔除 gold 自身）·
epochs 6 / batch 4 / max_len 160 / lr 1e-5 · **GPU 2 分 22 秒**。
收敛：loss 0.691→0.116、batch_acc 0.760→0.974（v2 混合 1422 条：0.500→0.069、0.829→0.985）。

### 3.3d pooling 定案：CLS（2026-09-12，回滚记录）

**用户要求"双塔 mean / 教师 CLS"→ 实测 mean 在短文本条款检索上显著更差 → 回滚 CLS**：

| 权重 | 推理 pooling | 训练 | MRR |
|---|---|---|---|
| dual_mix（CLS 训练） | CLS | — | **0.8698** |
| dual_mix 原权重 | mean | 未重训（训练/推理不一致） | 0.7578（-11.2pt） |
| dual_mix_mean（6ep） | mean | InfoNCE 6ep | 0.8274 |
| dual_mix_mean12（12ep） | mean | InfoNCE 12ep，loss 0.005/acc 1.0 | **0.7854** |

**结论（勿再改 pooling）**：
1. 训练/推理不一致直接 -11.2pt；重训也救不回——**12ep 训练集已收敛（loss 0.005）但 MRR 反而
   6ep→12ep 下降**，是过拟合训练分布，不是轮次不足。条款平均 82 字，mean 稀释关键词信号，
   CLS 保留序列级特征更有利 → **pooling = CLS 定稿**。
2. 所有历史指标（0.8698 / 0.9025 / 0.9142）都是 **CLS 口径**，未受污染；回滚后复验
   `dual_mix + RRF k=10` hit@5 0.962 / MRR 0.9025 **与历史完全一致**。
3. mean 实验产物已清理（模型/索引），实验数据保留 `data/phase7/pooling_ab*.json` +
   `scripts/ab_pooling.py`（可复现）。
4. **难负例口径**：现有 461 对已清洗难负例为 CLS 语义挖掘，**继续有效**（若再改 pooling 必须重挖）。

| A 同源 | **3290** | 399 | 候选与正样本同一本规范 | 第一优先级，限定条件/口径冲突都在这里 |
| B 跨源 band | **2205** | 413 | 跨源且 best_rank ∈ [5,12] | 第二优先级 |
| C 巨块 | **598** | — | `cand_len > 1200` | **排除**，见下 |

**两条修正旧假设的实测**

1. **跨源候选的 best_rank 分布是近乎均匀的**（rank 2..30 每档约 300 对）。
   旧文档"难负例密集区在 rank 10~30、top10 多为一眼易负例"的说法**不成立**——
   那只是 topN=30 截断造出来的形状。**band 宽度是纯粹的成本选择，不是质量最优区**，
   所以 `[5,12]` / `[5,20]` 之间没有"哪个更对"的问题，只影响我要判多少条。
2. **巨块候选是被低估的坑**：`cand_len > 1200` 的仅占 7%（A）/ 14%（B），
   却吃掉 **77% / 91% 的文字量**；最长的一条 122193 字符 = **一整本规范**。
   成因是切分断链把整节乃至整本吞成了一个"条款"。
   对 CE 训练有害无益：max_len 256 会把它截成随机前缀，模型只学到"长文本=负例"的伪特征。
   **分流后判定阅读量从 8.73M 字符降到 1.19M（−86%）**，待判 5495 对 = 10 批。
   巨块集中在少数规范：GB55015(36) / GB50205-2020(20) / DGJ08-11-2018(13) / DG-TJ08-61-2018(13)。
   正样本侧干净：422 条全部 ≤450 字符，无巨块。

**试标（50 对分层抽样，遍布 A 批 3290 对）**

| 指标 | 值 |
|---|---|
| `true_neg` | **50 / 50（100%）** |
| `false_neg` | **0**（95% 置信上界 ≈ 6%，按 rule of three） |
| 难度分布 | hard 18 / medium 20 / easy 12 |

两条解读：
1. **假阴性率极低**——因为 `mine_negatives.py` 已经剔除了正样本 clause_id 与其滑窗兄弟，
   同源候选基本都是"真负例"。所以清洗的**主要产出不是筛掉谁，而是把「为什么它是负例」写成理由**
   （限定条件 / 设备类型 / 数值口径 / 工序阶段 / 检测对象不同），这正是 P3 教师模型要学的判别依据。
2. **hard 占比 36%**：真正值钱的是"同规范 + 相邻条款号 + 主题高度相似"那一类
   （如 `GB50205` 4.2.3 钢板抽检 3 张 vs 4.3.3 型材抽检 3 根；`JGJ8` 4.5.7 极坐标法 vs 4.5.8 前方交会法；
   `GB55021` 6.5.8 粘钢构造 vs 6.5.6 外粘型钢；`JGJ107` 6.3.2 接头扭矩 vs 6.2.2 丝头自检）。
   **P3 的增益要按 difficulty 分层看**，只看整体 MRR 会把 easy 负例的收益算成"模型变强了"。
   → 这要求 `judgments.jsonl` 保留 `difficulty` 字段（已加，见第 5 节 P2 格式）。

### 修掉的三个根因（都在切分器里，都是"静默丢内容"型）

1. **正文最后一条把「附录 + 表格 + 条文说明」整段吞掉**。旧实现识别附录要求"标题后 7 行内
   有可解析的条款号"，而 JGJ94 附录的条款号被 OCR 打成 `A.O.l`／`D. O. 2`（字母 O 冒充 0），
   永远匹配不上 → 整本附录挂在最后一条正文下，**最长 122193 字符**。
   现在用四重判据认附录（正文已成本链 / 无目次点线 / 附近无第二个附录标题 /
   附近有 `表A…` 或 `A.0.1` 形式内容），并容忍 OCR 混淆数字。
2. **目次里的附录清单被误当真附录**。放松判据后 DGJ08-11 的 `附录R`（在目次里、后面跟着
   "本标准用词说明"）被误触发 → 整段进入附录模式，正文条款号再也不开新条，**实测丢 467 条正文**。
   加入"附近无第二个附录标题（8 行窗口）"排除。
3. **表格单元格数字被当成条款号**。旧判据只要求"号独占一行时下一行以中文开头"，
   于是表格里的 `7.5` + 下一行 `关10`（3 字）被认成条款 7.5。
   改为"下一行像正文：中文起头 + 数字占比 ≤ 50%"。
   另修 `_num_key`：附录号必须把**字母本身**编进排序键，否则 `B.0.1` 的键小于 `A.0.9`，
   被当成"号回退"而拒绝开新条，整个附录 B 挂到附录 A 下面。

### 切分阈值 ≠ 子块尺寸（**关键修正**，2026-09-11 第五轮）

需求原意：**合理送入 LLM 范围内的条款直接整条用，根本不需要滑窗与父子块**。旧实现把
`CHUNK_SIZE=700` 同时当"是否切分"的判据——任何 >700 字的条款都被切成多块，700~1200 字
（完全在 `MAX_PARENT_LEN` 预算内）的条款语义被无谓肢解。

修正后口径（`make_children` / `make_children_spans` 的 `threshold` 参数，默认 `MAX_PARENT_LEN`）：

- **条款 ≤ 1200 字 → 整条直用**（索引单元 = 条款全文，`uid=cid#0`），不做滑窗、不做父子块；
- **条款 > 1200 字 → 才按 700/100 递归切分**成子块（共享 `clause_id`），命中子块后回扩父块。

实测影响（同一 val 43 条）：单元 15132→**14916**（多子块父块 153 = 恰为 MAX_PARENT_LEN 定档
时的超限数，口径自洽）；BM25-only MRR `0.795→0.809`、双塔 α=0.3 MRR `0.878→0.890`——
**修复本身就是改进**（≈+1.1pt，来自"整条语义"而非"切碎的片段"）。α 最优点仍为 0.3。
回归测试：`tests/test_recursive_split.py::test_threshold_separate_from_size`。

**数据联动**：索引修正 → 检索命中的候选条款变化 → phase2 候选按新索引重生成
（A 3445 / B 2446 / C 443，原 3432/2449 作废）；试标 50 对中 49 对的新清单里已不存在
（候选集变了），已归档到 `judgments_pilot_archived.jsonl` 作方法论样本（结论仍有效：
true_neg 50/50、hard 36%），正式 `judgments.jsonl` 清零从零断点续做。

### 长度阈值 `MAX_PARENT_LEN = 1200`（≈ p99，定义见 `src/common/limits.py`）

按 13661 个父块的长度分布定档，在"保住多少条款整条回扩"与"送进 LLM 的长度预算"之间取平衡：

| 阈值 | 触发兜底窗口的父块 | 占比 | 这些父块占全文比例 |
|---|---|---|---|
| 700 | 362 | 2.6% | 37.1% |
| 1000 | 202 | 1.5% | 31.9% |
| **1200** | **153** | **1.1%** | **29.9%** |
| 1500 | 111 | 0.8% | 27.7% |
| 2000 | 72 | 0.5% | 25.1% |

取 1200：**98.9% 的条款整条回扩**（语义完整），只有 1.1% 走窗口兜底。

### 父子块回扩（`Corpus.expand`）

仅对 >1200 字的"过长条款"存在父子块（≤1200 的条款整条即单元，无子块概念）：

- 子块带 `start`/`end` 字符偏移（索引层写入 `units.jsonl`）；
- 同一 `clause_id` 的多个子块**去重**，只留最高分代表——排序键用 `(融合分, 原始分之和)`
  完整元组，避免温莎截断后的并列区按 `set` 无序顺序取代表（那样同一父块每次返回的子块都不同）；
- 父块 ≤ 1200 → 整条返回（`expanded=parent`）——**≤1200 条款命中即整条，天然满足**；
- 父块 > 1200 → 只回扩**命中子块周边**一段，窗口总长**恰好 = 1200**（`expanded=window`），
  并记录 `matched_span` / `window` 供溯源。

### 指标影响归因（实测，避免把噪声当结论）

同一套代码、同一 val(43) 条件下逐项隔离：

| 变量 | 对 MRR 的影响 |
|---|---|
| 语料重建（旧语料 @420/80 `0.8419` vs 新语料 @420/100 `0.8360`） | **−0.2%**，可忽略 |
| 子块尺寸 420 → 512 → 700（`0.836 / 0.844 / 0.840`） | ±1%，无明确优劣 |
| BM25 温莎边界重标定（`lo 37.43→23.20, hi 196.04→187.88`）后 α 最优点偏移 | α=0.4→**0.3**，MRR `0.866→0.878` |
| **切分阈值修正（700→1200，≤1200 整条直用）** | **MRR `0.878→0.890`（+1.1pt）**，BM25-only `0.795→0.809` |

工具：`scripts/ab_chunk_size.py`（`--clauses` 可指向 `data/corpus/_baseline_clauses.jsonl`
做"同代码跑旧语料"对照）。**结论：语料重建没有实质损害检索质量**；
与旧基线 0.895 的剩余差距落在 43 条饱和 val 的噪声区间内，
真正的判断要等 P7 黄金集（见第 6 节风险 1）。

> ⚠️ **一个必须知道的口径冲突**：子块取 700 字，但 `bge-small-zh-v1.5` 的位置编码上限是
> **512**。实测 11.2% 的单元超 512 字符、**5% 的真实 token 数超限会被静默截断**
> （旧实现用 420/80 正是为留这个余量）。A/B 显示三类尺寸指标差异 ≤1%，所以 700 可以保留；
> 但"子块尾部对向量无贡献"这件事是真实存在的，长子块的检索质量要靠**父块回扩**兜住。
> 若后续换用长上下文编码器（bge-m3 等），这个冲突自然消失。

## 4. 关键设计决策（含踩过的坑）

1. **条款切分不能只认 `第X条`**。现行 GB/JGJ 用数字条款号（`5.2.3`），旧实现只匹配 `第X条`，
   导致条款号严重错位（旧产物 `6.2.3` 的正文其实是 `7.2.6` 的内容）。rag2 改为：
   **正文 = 文档中第一段长度 ≥20 的「条款号严格递增链」**，同时处理三种真实排版
   （`4.1.4燃油…` 号文同行 / `1.0.1` 独占一行 / `…记录。6.2.3成孔…` 行内）。
2. **交叉引用与数值不能当条款起点**：号后接"条/款/项/规定/、/等"判为引用；号后必须紧跟中文
   （因此 `3.0m`、`表5.5.4` 不会被误切）。
3. **条文说明整段排除**：条文说明的条款号从 `1.0.1` 重启，与正文构成回退，靠"递增链"天然断开。
4. **faiss + 中文路径**：`faiss.write_index` 走 C++ `fopen`，Windows 非 ASCII 路径必失败 →
   `FaissStore` 改用 `faiss.serialize_index` 字节流 + Python 文件 IO。
5. **温莎截断会产生并列，必须加次级排序键**（本机新发现，已修）：
   截断把一批高分候选压成并列 1.0，而候选并集来自 `set()`（无序），只用融合分排序会让
   并列区顺序随机 —— 实测使 α=1.0（应等价于纯 BM25 排序）的 MRR 从 0.81 掉到 0.81 但**排名错乱**。
   修复：`_fuse` 同时返回"融合分 + 原始分之和"，排序键为 `(-fused, -raw)`。
   修好后 α=1.0 的指标与 BM25-only 完全对齐（0.884 / 0.810 / 0.827），验证修复正确。
6. **采样器按信息量打分**：第一版按"来源轮转取第 i 条"取样，结果全是「1.0.1 为…制定本规范」
   这类写不出问句的条款；改为对"含阈值判据 / 含数值+单位 / 长度 60~320"加分、
   对"总则套话 / 术语条 / 纯 1.0.x"减分后重采。
7. **数据校验前置**：`build_phase1_data.py` 校验每条 `clause_id` 真实存在——实际抓出 4 处
   id 笔误（`建筑与市政工程施工现场…` 写成 `建筑与市政施工现场…`、`…技术规程` 写成 `…技术规范`）。
   没有这一步，错 gold 会静默污染整条训练链。

### 迁移到 GPU 机器后新发现并修复的 4 个问题（2026-09-11 第二轮）

8. **`bootstrap.py` 会把"没装 torch"误报成"本机有 GPU"**（假阳性，危害大）：
   `gpu_info()` 在 `import torch` 失败时把 `cuda_available` 写成了字符串 `"unknown(torch missing)"`，
   而字符串是真值 → 第 3 节的 `if not g.get("cuda_available")` 判空失效、还打印出
   "↑ 本机有 GPU，P3/P4 可以在这里跑"。**用没装 torch 的解释器跑 check 时会得到一条完全错误的乐观结论。**
   修法：缺 torch 时 `cuda_available=None` + `error="torch missing"`，第 3 节按
   `None / False / True` 三分支分别给结论；并新增**物理显卡探测**（`Win32_VideoController`，
   不依赖 `nvidia-smi`——本机 NVML 初始化就失败、PATH 里也没有 nvidia-smi，
   所以只能把硬件探测当提示，能不能训一律以 `torch.cuda.is_available()` 为准）。

9. **faiss 在 GPU 环境里能不能 import 取决于导入顺序**（Windows DLL 搜索路径坑）：
   `faiss/_swigfaiss.pyd` 隐式依赖 Intel OpenMP（`libiomp5md.dll`）。`torch_gpu` 环境把这个 DLL
   只放在 `torch/lib/` 下，该目录**仅在 `import torch` 之后**才进 DLL 搜索路径 ——
   于是"先导 faiss"直接 `ImportError: DLL load failed while importing _swigfaiss`，"先导 torch"却正常。
   实测：单独 `import faiss` 失败 / `import torch; import faiss` 成功 / base 环境（Library/bin 里有该 DLL）正常。
   修法：`src/index/dense.py` 新增 `import_faiss()`——失败时把 `torch/lib` 挂上
   `os.add_dll_directory` 再重试，**不再赌导入顺序**。

10. **`--query-tower` 漏传会静默产生"看着合理其实错"的指标**：
    `dual_p1.faiss` 是微调后 doc 塔建的索引，若忘给 `--query-tower`，就会拿基座塔查微调索引，
    实测 **1.000/0.895 → 0.977/0.877**——不报错、不掉到明显异常，极易被当成真实结果写进结论。
    修法：`eval_retrieval.py` 检测到 `index` 以 `dual` 开头且未给 `--query-tower` 时自动补齐并打印提示；
    同时新增 `--device` 参数与输出里的 `device` 字段，便于区分"指标差异是设备造成的还是代码造成的"。

11. **依赖分级**：`fitz`(pymupdf) 原本和 numpy/torch 同级算"致命缺失"，
    而它只用于"从 PDF 重建语料"。结果是**语料已建好的机器上 check 直接报 ✗ 不可用，
    连冒烟检索都被跳过**（本机就是这样）。修法：拆 `CORE_PKGS`（缺则致命）与
    `OPTIONAL_PKGS`（缺则告警）；只有核心依赖齐全才跑冒烟。

### P4 / P5 —— 蒸馏（代码待写）

设计要点（已定，待实现）：
- 教师 = 冻结的 CrossEncoder；学生 = 双塔（query/doc 各一塔）。
- **pairwise 软 margin**：同一 query 的 (正, 真难负) 对，教师给 `s_pos`、`s_neg`，
  软目标 `p = σ((s_pos − s_neg) / τ_t)`，学生 `q_i = σ((d(q,pos) − d(q,neg)) / τ_s)`，
  损失 `−[p·log q + (1−p)·log(1−q)]`；起始 `τ_t = 1.0`、`τ_s = 0.05`（需标定）。
- 只用 P2 清洗后的「正 + 真难负」，与 P3 同一套数据（满足"同一套数据集"的要求）。
- 迭代（P5）：用蒸馏后的新 doc 塔重建索引 → 重跑 `mine_negatives.py` → 增量清洗 →
  扩充 `ce_train.jsonl` → 二次蒸馏。
